# Qwen3-TTS на CM3588 — RTF 2.0x (llama.cpp + GGML)

Высокопроизводительный C++/Python пайплайн для [Qwen3-TTS](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-0.6B-Base) на FriendlyElec CM3588 (RK3588).

**Достигнут RTF 2.0x** — самый быстрый Qwen3-TTS на edge-железе (vs RTF 5.5x на RKLLM).

## Архитектура

```
                   ┌─────────────────────┐
Текст ─────────────┤  Токенизатор + Embed├──→ эмбеддинги
                   └────────┬────────────┘
                            │
         ┌──────────────────▼──────────────────┐
         │    llamacpp_talker_server.py         │
         │    llama.cpp GGUF Q4_K_M (A76)      │
         │    ~30-35 ток/с, ~30мс/шаг           │
         └──────────────────┬──────────────────┘
                            │ unix socket
         ┌──────────────────▼──────────────────┐
         │    code_pred_server (GGML Q4_0)     │
         │    в 4.8x быстрее ONNX              │
         │    ~55мс/шаг                         │
         └──────────────────┬──────────────────┘
                            │ unix socket
         ┌──────────────────▼──────────────────┐
         │    vocoder_server.py                 │
         │    RKNN FP16 (NPU, 3 ядра)          │
         │    stateful-стриминг, швов нет       │
         └──────────────────────────────────────┘
```

Три независимых сервера общаются через Unix-сокеты. Каждый можно перезапустить отдельно.

## Производительность

Тестировано на FriendlyElec CM3588 (RK3588 4xA76+4xA55, 32GB RAM):

| Компонент | Время | Примечание |
|---|---|---|
| Talker (llama.cpp A76) | ~30мс/шаг | GGUF Q4_K_M, 469 МБ |
| Code Predictor (GGML Q4_0) | ~55мс/шаг | **в 4.8x быстрее ONNX** |
| Вокодер (ONNX FP32) | ~5.0с/64-tok | Overlap-crossfade |
| **Итого RTF** | | **2.0x** |

Замерено на плате RK3588 без Axera NPU (пиновка на 4×A76, русский текст): как есть — RTF 3.9-4.4x.
Code predictor при этом стоил 199 мс на запрос из 15 шагов; после удаления нод
`ggml_cast(ffn_down, F32)` в `qwen3-tts.cpp/src/tts_transformer.cpp` (CPU-бэкенд ggml принимает
F16/Q8_0-веса прямо в `mul_mat`; cast-нода демоквантит 12.6 MB на слой на шаг, 75 раз на токен)
— 64 мс, генерация 4.5 → 11.5 tok/s, **RTF 2.6x**. Перенос вокодера на NPU RK3588 в **RKNN FP16**
(без потерь, SNR 56.8 дБ — см. ниже) даёт streaming **RTF 1.8x** (генерация 8.9 tok/s параллельно
вокодингу, первый чанк ~3 с).

### Вокодер: FP32 ONNX на CPU против RKNN на NPU

Вокодер использует **Snake activation** (`x + sin²(α·x)/α`), несовместимую с *квантизацией*:
- **RKNN Q8**: быстрее в 1.75x, но слышен шум (SNR 9.5 дБ на случайной калибровке, 13.4 дБ на реальных записанных запросах)
- **ONNX INT8**: в 3x *медленнее* + плохое качество (SNR 4.2 дБ)
- **AX650N NPU**: Conv1D dilation=9 не поддерживается
- **MNN GPU**: ошибка broadcast в SineGen

**RKNN FP16 (`w16a16`) — это не квантизация, и она без потерь**: SNR 56.8 дБ, corr 1.0000 против
FP32-референса при скорости в 1.34x выше 4 ядер CPU — и работает на NPU, не отнимая ядра A76 у
code predictor'а. Поэтому streaming теперь выигрывает. Деплой:
`python3 scripts/convert_vocoder_rknn.py --model vocoder_traced_64.onnx` (без `--quantize`),
`VOCODER_MODEL` на результат, и `PYTHONPATH=dual_npu/rknnlite_shim` (шим даёт API `RKNNLite` поверх
`librknnrt.so` для платных Python'ов новее, чем собраны lite2-колёса).

### Швы чанков вокодера

Декодер WavTokenizer **каусален**: токен, озвученный в начале чанка с нулевым паддингом, — это
*другая волна*, чем тот же токен в середине последовательности (замерено: corr 0.445, SNR 0.3 дБ).
Исходный overlap-crossfade на 16 токенов с нулевым паддингом смешивал две несовпадающие волны —
слышимый «двойной голос» на каждой границе. Чанкирование теперь работает слоями, каждый слой
замерен против одиночного 256-токенного ONNX-прогона тех же кодов:

- **Реальный контекст вместо паддинга**: перед чанком дописываем хвостовые токены предыдущего
  чана (48 для 112-слотовой модели; короткий хвостовой чан заполняет контекстом все свободные
  слоты), их аудио срезается. SNR границы: 4.1 дБ @16 ctx → 9.9 @32 → 19.1 @48 → 19.8 @60
  (насыщение; рецептивное поле намного шире).
- **Швы в паузах**: соседние сегменты нельзя кроссфейдить (сумма волн, декоррелированных на
  19 дБ = гребенчатый треск), а выбрасывать речь слышно — шов *переезжает*: самый длинный
  непрерывный тихий участок (≥150 мс, 20 мс-RMS < 25% RMS окна) в последних 3 с чанка становится
  его концом, и `stitch()` там выбрасывает только тишину (равноэнергетические окна cos/sin).
  Если шов посреди фразы — 20 мс равноэнергетический микро-бленд в самой тихой точке рядом.
- **Warmup-truncate** (overlap в стиле CosyVoice): каждый чанк декодируется на 2 токена дальше
  своего шва, следующий стартует от шва, и общая зона — содержащая транзиент конвейеров без
  контекста в голове следующего чана — выбрасывается в паузе или блендится на громком шве.
  max|diff| шва против одиночного референса: 97–108 m → 0.1–9.5 m.

Итог end to end (RKNN FP16, 112 слотов): глобальный SNR против одиночного прогона 26–32 дБ,
локально на швах 25–57 дБ; остаток — FP16-релаксация перечита после шва. Точный фикс — stateful
экспорт ниже, у него швов нет вовсе; эта схема остаётся фолбэком для сборок без NPU.

### Вокодер: stateful-стриминг (без чанков)

Декодер WavTokenizer v2 **полностью каузален**, поэтому всю его историю можно держать в I/O самой
модели, а не перезадавать на каждый чанк. `scripts/export_vocoder_stateful.py` экспортирует один
шаг стриминга: хвосты всех каузальных свёрток (`(k-1)*d` входов, `ceil((k-1)/s)` для
транспонированных) и скользящее окно KV пре-трансформера (71 ключ × 8 слоёв × 2 × 16 голов × 64)
упакованы в **один плоский float32 кэш — 1303424 чисел, 5.2 МБ — который является и входом, и
выходом**:

```
audio_codes [1,16,64] int64 ─┐
freqs_in    [64,32]   fp32  ─┤→ шаг →  audio_values [1,122880]   (64 токена = 5.12 с 24 кГц)
cache_valid [1]       fp32  ─┤          cache_out   [1303424] fp32
cache_in    [1303424] fp32  ─┘
```

Формы фиксированы везде, поэтому конвертация как у любого вокодера:

```bash
python3 scripts/export_vocoder_stateful.py --codes-length 64 \
    --output models/vocoder_stateful_64.onnx
python3 scripts/convert_vocoder_rknn.py --model models/vocoder_stateful_64.onnx --stateful \
    --output models/vocoder_stateful_64_fp16.rknn
# на плате: VOCODER_MODEL=/root/tts-rknn/vocoder/vocoder_stateful_64_fp16.rknn (в имени обязано
#          быть 'stateful' — именно это включает стриминговый путь в сервере и клиенте)
```

Протокол (тот же сокет, без новых опкодов): сервер **буферизует** токены запроса и шагает только
полными группами по 64, поэтому граница запроса в середине группы никогда не зери-паддится (паддинг
пишет тишину в кэши — только это стоило 25 дБ end to end). Запрос с `n_tokens=0` это **флеш**:
озвучивает остаток < 64 токенов и возвращает его аудио, затем обнуляет состояние. Клиент шлёт такой
reset один раз в начале реплики (пустой флеш) и один раз после последнего чанка, а куски просто
конкатенирует — без stitch, без overlap, без швов.

FP16-сборка на NPU продавила четыре неочевидных решения, каждое измерено:

- **Углы RoPE приходят входом, cos/sin считаются в графе.** Подавать cos/sin входами взрывает
  fp16-конвейер (rms q 0.68 → 120). Сырые углы `pos*inv_freq` доходят до ~1e4, где fp16 ulp = 0.5,
  поэтому хост редюцирует их по модулю 2π (значения ≤ 6.28, ulp 0.004).
- **Attention mask — константа графа на −100** на *относительной* сетке (`qp-kp`), то есть не
  зависит от номера шага. −3e4 протекает через NPU-softmax (внимание становится равномерным); а
  абсолютная маска поданная *входом* вместе с cos/sin в графе роняет рантайм платы в SEGFAULT.
- **Валидность кэша — скалярный вход** (`cache_valid` = 0 на первом шаге реплики, дальше 1).
  Выводить её из данных кэша (цепочка Abs/ReduceSum/Clip) — минус 30 дБ.
- **История KV присоединяется константными matmul-селекторами** (`A@cache_k + P@k`), а не Concat:
  путь Concat в RKNN портит sliding-window attention (9.5 дБ против 56.8 дБ).

Замеры на плате, один и тот же русский текст на 200 токенов, `--streaming`, против одиночного
256-токенного ONNX FP32 прогона тех же кодов:

| Вокодер | Глобальный SNR | Зоны по 64 токена | Генерация | Ожидание вокодера | RTF |
|---|---|---|---|---|---|
| швы чанков (112 слотов) | 26.4 дБ | 57.5 / 21.1 / 29.7 | 6.5 tok/s | 6.0 с | 2.6x |
| **stateful-стриминг** | **48.0 дБ** | 56.2 / 44.5 / 51.1 / 53.4 | 7.5 tok/s | 0.0 с | **1.9x** |

Stateful нигде в реплике не проседает ниже 44 дБ (у чанковой схемы минус 30 дБ после первого шва),
и он перестаёт отъедать ядра A76 у code predictor — поэтому генерация тоже ускоряется.
FP32-самопроверка экспорта (пошагово против полного декода, `--check-only`) даёт 48.8 дБ — это
шум fp32-аккумуляции в matmul-селекторах KV, а не смысловая ошибка.

### Путь оптимизации

| Версия | Code Predictor | Вокодер | RTF |
|---|---|---|---|
| Базовая (RKLLM talker) | ONNX 1-поток (374мс) | RKNN Q8 | 5.5x |
| + llama.cpp talker | ONNX 1-поток (374мс) | RKNN Q8 | 5.5x |
| + 2-поточный ONNX CP | ONNX 2-потока (265мс) | RKNN Q8 | 4.4x |
| + GGML Q4_0 CP | **GGML (55мс)** | RKNN Q8 | 2.2x |
| + ONNX FP32 вокодер | GGML (55мс) | **ONNX FP32** | **2.0x** |
| + фикс cast ffn_down | GGML Q8_0 (64мс/15 шагов) | ONNX FP32 | 2.6x (3.0x стриминг) |
| + RKNN FP16 вокодер на NPU | GGML Q8_0 (64мс/15 шагов) | **RKNN FP16 (чанки по 112)** | 1.8x |
| + stateful-стриминг вокодер | GGML Q8_0 (64мс/15 шагов) | **RKNN FP16 stateful (без чанков)** | **1.9x** |

Три последние строки измерены на этой плате (русский текст, 4×A76; строка с фиксом cast —
не стриминг, остальные две `--streaming`); времена CP в строках выше взяты из апстрима.
1.8x и 1.9x — разные тексты (137 / 200 токенов): A/B stateful против чанкового вокодера
со швами на одном тексте в 200 токенов даёт 2.6x → 1.9x.

TTFB стрима на stateful-пути — **≈9.3 с**: первый чанк из 64 токенов уходит в вокодер на +5.7 с,
шаг stateful-вокодера 3.6 с (на FP32-CPU-вокодере было 19–23 с). Code predictor — 63% CPU-времени
на токен — единственный компонент, которому NPU *не* помогает: stateful-граф шага
(`scripts/export_code_predictor_stateful.py` + `scripts/convert_code_predictor_rknn.py`,
проверен: 15/15 кодбуков и 2.8e-05 по логитам первого шага против fp64-эталона) идёт на трёх ядрах
NPU за **23.2 мс/шаг против 4.3 мс/шаг на 4×A76 с GGML Q8_0 — в 5.4 раза медленнее**. 157 MB
FP16-весов за 23 мс = 6.8 GB/s, то есть в ~6 раз ниже плато платы (~40 GB/s): платится за оверхед
на операцию, ~75 крошечных GEMV (S=1) плюс 1.3 MB KV-кэша через границу рантайма на каждый вызов.
NPU окупается на настоящих GEMM (чанк вокодера на 64 токена), а не на 16 последовательных шагах по
одному токену. Путь `.rkllm` закрывает та же арифметика: CPU-путь уже читает 157 MB за 4.3 мс =
36.5 GB/s, то есть сидит на плато DRAM платы (~40 GB/s), а измеренная эффективная скорость чтения
весов у RKLLM на этой плате — ~15 GB/s.

Длинные реплики больше не обрезаются. Контекст talker'а — `N_CTX` (по умолчанию 2048; `N_BATCH`
отделён и мал: ggml compute buffer размеряется именно n_batch — 1243 MiB при 2048 против
311 MiB при 512, на тех же ядрах, что занимает code predictor), а бюджет запроса —
`min(MAX_TOKENS, N_CTX − prefix − 1)`, так что длинный текст заканчивается собственным EOS модели.
Замер: запрос из 189 текстовых токенов даёт 430 токенов (26.1 с аудио) при 6.6 tok/s, 73 с wall
(RTF 2.8x на 26-секундной реплике против 1.9x на 16-секундной).

## Быстрый старт

```bash
# Одиночный синтез
bash dual_npu/launch_qwen3_tts.sh "Привет, как дела?"

# Режим демона (постоянные серверы)
bash dual_npu/launch_qwen3_tts.sh --daemon

# Клиент (при работающем демоне)
python3 dual_npu/tts_client.py "Текст для синтеза" --language russian

# Со стриминг-вокодером (параллельно с генерацией)
python3 dual_npu/tts_client.py "Длинный текст..." --language russian --streaming
```

## Варианты Code Predictor

Пайплайн поддерживает три бэкенда (авто-выбор):

| Бэкенд | Скорость | Качество | Примечание |
|---|---|---|---|
| **GGML Q4_0** (по умолч.) | 55мс/шаг | Лучшее | Требует [qwen3-tts.cpp](https://github.com/nickovchinnikov/qwen3-tts.cpp) |
| C++ ONNX Runtime | 240мс/шаг | Хорошее | Встроен, `dual_npu/code_predictor_cpp/` |
| Python ONNX Runtime | 248мс/шаг | Хорошее | Fallback, без компиляции |

## Подготовка моделей

1. Извлечь talker как Qwen3: `python3 scripts/extract_talker_as_qwen3.py`
2. Конвертировать в GGUF: `python3 scripts/convert_talker_gguf.py`
3. Извлечь эмбеддинги: `python3 scripts/extract_embeddings.py`
4. Экспортировать code predictor: `python3 scripts/export_code_predictor_weights.py`
5. Экспортировать вокодер: `python3 scripts/export_vocoder_traced.py`
5b. (Рекомендуется, NPU) Экспортировать **stateful-стриминг** вокодер и сконвертировать его:
   `python3 scripts/export_vocoder_stateful.py --codes-length 64 --output models/vocoder_stateful_64.onnx`,
   затем `python3 scripts/convert_vocoder_rknn.py --model models/vocoder_stateful_64.onnx --stateful`
   — см. [Вокодер: stateful-стриминг](#вокодер-stateful-стриминг-без-чанков).
6. (Опционально) Конвертировать GGML code predictor: [qwen3-tts.cpp](https://github.com/nickovchinnikov/qwen3-tts.cpp)
7. (Рекомендуется) Ужать и квантизовать GGML-модель code predictor:
   `python3 scripts/quantize_code_predictor_gguf.py --in <f16.gguf> --out <cp-q8_0.gguf>`, затем
   `CP_GGML_MODEL` на результат. Оставляет только тензоры, которые code predictor реально читает, и
   пакует matmul-веса в Q8_0: 1745 MB → 183 MB, RSS CP-сервера на RK3588 1764 → 217 MB, скорость без изменений.

См. [docs/MODEL_CONVERSION.md](docs/MODEL_CONVERSION.md).

## Сравнение с CosyVoice3

| | Qwen3-TTS (этот проект) | [CosyVoice3](https://github.com/nickovchinnikov/cosyvoice3-axera-russian) |
|---|---|---|
| RTF | 2.0x | **1.26x** |
| Архитектура | Talker → CP → Vocoder | LLM → Flow DiT → HiFT |
| NPU (AX650N) | Не используется | Flow DiT на NPU |
| Качество | Хорошее | Хорошее |

CosyVoice3 быстрее, потому что Flow DiT (MatMul+Attention) работает на AX650N NPU, освобождая CPU. В Qwen3-TTS нет компонентов, подходящих для NPU *для квантизации* — Snake activation вокодера убивает Q8/INT8 — но неквантизованный путь RKNN FP16 потерь не несёт, поэтому вокодер всё же работает на NPU RKNN (см. выше).
